# 0015. Валидация и идемпотентность intents

- Статус: Принято. Дополняет [0007](0007-protocol-encoding.md).
- Дата: 2026-10-21

## Контекст

ADR-0007 разрешил `i64` в TS как `number` и генерацию id на клиенте. Нужны гарантии, что ни одно
значение не потеряет точность в JS, что id имеют ожидаемый формат и что повтор intent (реконнект,
переотправка `pending_ops` по ADR-0004) не применяется дважды.

## Решение

### Структурная валидация (`dnd-protocol::validate`)

- Все целые, уходящие в TS или приходящие от клиента, в пределах ±(2^53−1) (`MAX_SAFE_INTEGER`):
  `expected_version`, `last_seq`, `seq`, `ts`. Нарушение → `Rejected { invalid, field }`.
- Версии и `seq`, которые порождает сервер, растут через `checked_next`: на границе — отказ
  (`invalid: version`, `seq_exhausted`), а не потеря точности.
- `intent_id`, id конверта и id создаваемых сущностей — UUIDv7 (версия 7, вариант RFC 9562).
  Иначе `Rejected { invalid }`.
- Валидация вызывается первой в `dnd_game_core::apply`, до проверки прав, поэтому её получают и
  локальный сервер, и сервер сессий.

### Коллизии и права

- Id уникальны **между всеми видами сущностей**: новая карта не может занять id токена или персонажа.
  Коллизия → `Rejected { already_exists }`.
- Права никогда не выводятся из id или его формата/времени: только роль и текущее состояние.

### Идемпотентность

- `intent_id` — ключ идемпотентности. Сервер (и локальный сервер) помнит исходы недавних intents
  (`dnd_game_core::RecentIntents`, 4096 записей). Повтор того же `intent_id` возвращает **исходный**
  результат (`IntentOutcome`) и ничего не применяет, не пишет и не рассылает повторно — даже если
  payload отличается или повтор сейчас прошёл бы иначе. Новая попытка = новый `intent_id`.
- Принятые intents переживают перезапуск: при открытии кампании последние 4096 восстанавливаются из
  `event_log.intent_id` (индекс уже есть). Отказы помнятся только в пределах запуска: они ничего не
  записали, поэтому повтор после перезапуска безопасно вычисляется заново.
- Ошибка хранилища исход не фиксирует: такой intent можно повторить с тем же id.
- Это основа реконнекта (клиент переотправляет неподтверждённые intents) и переигрывания
  `pending_ops` по ADR-0004.
- `IntentOutcome { accepted { seq } | rejected { reason } }` перенесён в `dnd-protocol`: он нужен и
  серверу сессий.

## Последствия

- Клиенты обязаны генерировать UUIDv7 (`crypto.randomUUID` даёт v4 и будет отклонён).
- Тестовые стратегии proptest генерируют только валидные v7 id; отдельный тест это проверяет.
