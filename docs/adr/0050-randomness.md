# 0050. Рабочая случайность: CSPRNG вне ядра

- Статус: Принято
- Дата: 2026-11-08

## Контекст

ADR-0001 требует, чтобы ядро не делало I/O и получало случайность снаружи. Фактически рабочий
поток был предсказуем: сервер выводил seed из публичного `SessionId`, локальная игра — из
системных наносекунд, а `CampaignEngine` заново создавал `SplitMix64` при каждой загрузке.
Игрок, знающий id сессии, мог воспроизвести броски; перезапуск возвращал ту же
последовательность. Дорожная карта A2 требует криптостойкий рабочий источник, отдельный от
детерминированного тестового RNG.

## Решение

### Источник

В `dnd-db` добавлен `OsRng` — реализация `GameRng`, которая берёт каждое число из системного
CSPRNG через `getrandom` (зависимость уже введена ADR-0022 для секретов). Seed не выводится из
идентификаторов или времени и нигде не публикуется; после перезапуска поток продолжается с
новой энтропии.

- Конструктор `OsRng::new()` делает одну пробную выборку: при недоступном источнике сессия не
  открывается, а не падает посреди хода.
- Если источник отказывает уже во время игры, стол не останавливается: поток продолжается из
  стартового seed, а отказ пишется в лог. Это деградация, а не штатный режим.
- Ядро остаётся без I/O: `GameRng` передан в `apply`, как и раньше.

### Внедрение

`CampaignEngine::load(db, window, rng, now_ms)` принимает `Box<dyn GameRng + Send + Sync>`.
Сервер и локальная игра передают `OsRng`; тесты — `SplitMix64` с фиксированным seed, поэтому
они по-прежнему детерминированы. `CampaignEngine` получает ручной `Debug` (trait-объект его не
выводит).

### Повтор и отказ

- Повтор принятого `intent_id` возвращает сохранённый исход (`Accepted`/`Rejected`) и не
  порождает новых событий и бросков — правило ADR-0015, теперь проверенное и на броске костей:
  следующее значение RNG совпадает с контрольным движком, не видевшим повтора.
- Неудачная запись не оставляет следов: состояние, счётчик `seq` и чат не меняются, исход не
  запоминается. Бросок на этом пути никто не видел, поэтому повтор после ошибки записи — новая
  попытка с новой случайностью; повтор после потерянного ответа, когда запись прошла, возвращает
  сохранённый результат без нового броска.

## Последствия

- Броски в рабочей сессии нельзя воспроизвести по id сессии или по времени запуска.
- Каждое число — системный вызов. Броски и идентификаторы сообщений невысокочастотны; если
  профиль A4.1 покажет заметную стоимость, буферизация добавится отдельно, не меняя политику.
- Детерминированные тесты обязаны передавать свой RNG в `load`; «магического» seed в движке
  больше нет.
- Commit-reveal и проверяемая честность бросков остаются пост-MVP: это отдельная задача
  протокола, а не свойство рабочего RNG.

## Рассмотренные альтернативы

- **Хранить seed кампании в файле.** Даёт воспроизводимость, но и предсказуемость для того, у
  кого есть файл; кроме того, повторная загрузка продолжала бы тот же поток.
- **ChaCha20 с 256-битным seed.** Меньше системных вызовов, но требует новой зависимости и
  ручного управления состоянием; при текущей частоте выигрыш не оправдан.
- **`rand` + `ThreadRng`.** Ещё одна зависимость ради того же результата; `getrandom` уже есть.
