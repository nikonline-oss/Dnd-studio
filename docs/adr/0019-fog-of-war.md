# 0019. Туман войны

- Статус: Принято
- Дата: 2026-10-23

## Контекст

Этап 2a, шаг 5: мастер вручную открывает и закрывает области карты (CLAUDE.md §12, «ручной
туман»). С пользователем решено: туман — **векторные операции** (прямоугольник и кисть), а не
растровая маска. В схеме (§6) у карты уже есть колонка `maps.fog` (JSON).

Требования:

- через тот же пайплайн intents (ADR-0001), права проверяет ядро, только GM и Co-GM (§5);
- состояние детерминировано и одинаково на сервере и клиенте;
- размер данных ограничен: туман попадает в снапшот и в одну строку SQLite;
- рисование кистью не должно конфликтовать с правками карты (имя, сетка), которые проверяют
  версию (ADR-0003).

## Решение

### Модель

- Туман карты = начальное состояние `covered` (вся карта закрыта или открыта) + упорядоченный список
  операций `FogOp { id, kind: reveal | hide, shape }`. Видимая область получается последовательным
  применением операций: `hide` добавляет туман, `reveal` вырезает.
- Формы, все координаты в Units16 (ADR-0016):
  - `rect { x, y, width, height }` — прямоугольник внутри карты, `width, height > 0`;
  - `brush { radius, points }` — круги радиуса `radius`, протянутые вдоль ломаной `points` (плоский
    массив `[x0, y0, x1, y1, …]`), `1..=512` точек, `1 ≤ radius ≤ 256 · 16`.
- Карта без тумана не имеет записи (равно `covered: false` без операций). Новая карта — без тумана;
  мастер включает его кнопкой «Закрыть всё».
- Туман **не входит в `MapDto`**: `map_updated` несёт карту целиком, и переименование тащило бы
  мегабайт тумана. Снапшот несёт отдельный список `fog: FogDto[]`.

### Протокол

- `apply_fog { map_id, op }` — добавить операцию. `op.id` — новый UUIDv7 (политика `Create`): повтор
  события не рисует форму дважды, `evolve` пропускает уже известный `id`. Версия карты **не меняется**,
  поэтому кисть не вызывает `stale_version` у параллельной правки сетки.
- `reset_fog { map_id, covered }` — удалить все операции и задать начальное состояние (LWW).
- События: `fog_applied { map_id, op }`, `fog_reset { map_id, covered }`. Туман неизвестной карты
  игнорируется (как `token_moved` неизвестного токена).
- Лимиты на карту: **4096 операций** и **65 536 точек кисти** суммарно (прямоугольник точек не
  тратит). Это ~1 МБ JSON в худшем случае. Превышение → новый код отказа
  `limit_exceeded { limit: "fog_ops" | "fog_points" }`; UI предлагает сбросить туман.
  «Запекание» операций в растр — пост-2a.

### Хранение

- `maps.fog` = `{"covered": bool, "ops": [FogOp…]}`. `fog_applied` дописывает операцию на месте
  (`json_insert(…, '$.ops[#]', …)`), `fog_reset` заменяет значение. `upsert_map` колонку не трогает.
  Новых таблиц и миграций нет.

### Рендер (клиент)

- Туман рисуется в `RenderTexture` не больше **2048 px** по большей стороне (на карте 16 384 px —
  8 логических единиц на тексель; мягкий край тумана здесь уместен), растянутую на карту. Это
  16 МиБ видеопамяти вне зависимости от размера карты и числа операций.
- Новая операция дорисовывается поверх текущей текстуры (`hide` — цветом тумана, `reveal` —
  режимом `erase`); полная перерисовка — только при сбросе, смене карты и после смены фона/размера.
- Мастер видит туман полупрозрачным (контур закрытого), игрок — непрозрачным.
- Инструменты мастера: прямоугольник и кисть, каждый в режиме «открыть»/«скрыть», размер кисти,
  «Закрыть всё», «Открыть всё». Кисть прореживает точки (не ближе половины радиуса друг к другу) и
  делит длинный мазок на несколько операций по 512 точек.

## Последствия

- Туман сейчас **не защищает изображение карты**: тайлы фона отдаются целиком, игрок технически
  может открыть скрытые места. Настоящая защита — серверная фильтрация видимости (этап 4) и/или
  отдача игрокам заранее замаскированных тайлов. Локально в 2a за столом один мастер, поэтому
  это не уязвимость сейчас.
- Отмена операций (undo) возможна позже: у каждой операции есть `id`, понадобится intent удаления
  по `id` и полная перерисовка.
- Динамическое освещение и линия видимости (P2) не заменяют ручной туман, а работают поверх.

## Рассмотренные альтернативы

- **Растровая маска в БД** (PNG на карту). Простой рендер и постоянный размер, но каждое изменение —
  перезапись картинки, конфликты целиком, нет истории и идемпотентности по операции. Отвергнуто
  вместе с пользователем в пользу векторных операций.
- **Туман внутри `MapDto`.** Меньше типов, но любой `map_updated` нёс бы весь туман, а кисть меняла
  бы версию карты и конфликтовала с правками сетки. Отвергнуто.
- **Отдельная таблица `fog_ops`.** Дописывание без переписывания JSON, но новая таблица сверх §6
  ради данных, которые всегда читаются целиком вместе с картой. Колонка `maps.fog` уже в схеме;
  при лимите ~1 МБ перезапись строки дешёвая. Отвергнуто для 2a.
