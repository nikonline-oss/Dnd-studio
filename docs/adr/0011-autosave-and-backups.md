# 0011. Автосохранение и бэкапы

- Статус: Заменён [0014](0014-write-through-persistence.md) в части автосохранения; бэкапы и восстановление действуют
- Дата: 2026-10-21

## Контекст

CLAUDE.md §10: WAL; debounce грязного состояния 2 с; flush каждые 5 мин; graceful shutdown;
`quick_check` при открытии и восстановление из бэкапа; бэкап перед миграцией; не более 5 бэкапов.

## Решение

- `LocalServer::submit` применяет intent к состоянию в памяти сразу и ставит батч в очередь. Запись в
  SQLite (`event_log` + проекция, одна транзакция) — `flush()`:
  - через 2 с тишины после последнего изменения, но не позже 10 с от первого несохранённого
    (иначе непрерывное перетаскивание токенов откладывало бы запись бесконечно);
  - каждые 5 минут — flush + `wal_checkpoint(TRUNCATE)`;
  - при закрытии кампании, смене кампании, `Ctrl+S` (`campaign_save`) и при выходе из приложения
    (выход откладывается до сохранения, не дольше 10 с).
- При ошибке записи очередь сохраняется для следующей попытки; UI получает `SaveStatusChanged` и
  показывает «Ошибка сохранения» в строке статуса.
- Цена: при аварийном завершении теряются изменения последних ≤ 10 с.
- Бэкапы: перед миграцией (ADR-0008) и при открытии, если самому свежему больше 24 ч — иначе после порчи
  файла восстанавливать было бы не из чего. Хранится 5.
- `quick_check` при открытии; повреждённый файл → `IpcError { kind: Recoverable, code: campaign_corrupt }`;
  UI предлагает «Восстановить из последнего бэкапа». Команда восстановления работает только с папкой,
  открытие которой только что упало (путь хранится в Rust, фронтенд путей не передаёт).
- Safe Mode (счётчик крашей, запуск без плагинов) переносится на этап 3: без плагинов ему нечего отключать.

## Последствия

- Состояние в памяти может опережать диск на ≤ 10 с; это видно пользователю в строке статуса.
- Для сервера сессий (этап 4) политика может быть строже (запись до рассылки событий).
