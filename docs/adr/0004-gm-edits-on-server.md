# 0004. Редактирование кампании GM, пока она на сервере

- Статус: Принято
- Дата: 2026-10-20

## Контекст

После загрузки кампании на сервер источником истины становится сервер, но GM продолжает готовиться —
в том числе офлайн. Нужен предсказуемый способ слить правки без потери данных.

## Решение

- GM подключён к сессии → его правки идут intents через сервер; локальная БД — реплика, применяющая events.
- GM офлайн с выгруженной кампанией → правки пишутся в локальный журнал `pending_ops` (intent + base version).
  При подключении журнал отправляется на сервер по порядку.
- Конфликт (`StaleVersion`) → серверная версия остаётся, конфликтующая правка попадает в панель «Конфликты»
  с diff и кнопками «применить мою поверх» / «отбросить».
- Ассеты адресуются по SHA-256 — конфликтов не бывает, докачиваются по хэшу.
- Остановка сессии → клиент забирает финальный SQLite, делает бэкап локального и заменяет его.
- Кампания в статусе «на сервере» помечается в UI (строка статуса + бейдж в навигаторе).

## Реализация клиента

- При хостинге сохраняются путь локальной кампании в `RemoteEntry.local_campaign` и локальная метка
  `campaign_meta.local.remote_session`. Открытие этой копии после перезапуска продолжает собирать очередь.
- Перед отправкой и заменой проверяются точная связь сервер/сессия и исходный пользователь GM.
  Несовпадение блокирует синхронизацию; уже связанную копию нельзя повторно хостить в другую сессию.
- Принятые локальные события и соответствующий `IntentEnvelope` пишутся одной SQLite-транзакцией.
  Отказ ядра и ошибка проекции не оставляют операцию в очереди. Повтор использует тот же `intent_id`.
- При реконнекте операции отправляются по порядку; первый отказ останавливает зависимые операции.
  «Применить мою поверх» использует новую версию и новый `intent_id`; «Отбросить» удаляет операцию.
- Перед регистрацией офлайн-ассета передаются WebP, аудио или архив плагина. Сервер проверяет роль,
  размер, формат и SHA-256; ошибка передачи сохраняет операцию и зависимые правки в очереди.
- Сверка локальной копии использует проверенный архив сервера, резервную копию перед заменой и откат
  при неудаче открытия. Локальные оригиналы ассетов и неразрешённые операции сохраняются.
- Замена SQLite проходит через подготовленный и синхронизированный `campaign.sqlite.sync-new` и
  сохранённый `campaign.sqlite.sync-old`. Открытие после сбоя восстанавливает старый файл, если основной
  отсутствует, повреждён или не загружается. Непригодный файл сохраняется отдельно для диагностики.
- После загрузки авторитетной копии оставшиеся операции заново строят предварительное представление.
  `pending_ops.projected` (миграция 0017) и локальная метка `local.speculative` исключают повторную
  проекцию и смешивание предварительных событий с серверной последовательностью. Версии для просмотра
  пересчитываются; исходные конверты для сервера сохраняются. Сравнение конфликтов использует серверные данные.
- Онлайн-события последовательно проецируются в копию без ожидающих правок. После полного реснапшота
  проверяется последовательность и при необходимости заново загружается авторитетная копия.
- Остановка сессии требует разрешить оставшиеся конфликты; после остановки клиент получает финальную
  копию и снимает локальную метку удалённой сессии.
- Офлайн-представление предварительное: результаты триггеров и RNG окончательно определяет сервер
  при переигрывании намерений.
- Старые сохранённые подключения без `local_campaign` продолжают работать онлайн; связь с локальной
  копией создаётся при новом хостинге.

## Последствия

- Один и тот же пайплайн intents используется онлайн и для переигрывания офлайн-журнала.
- Панель офлайн-правок показывает сравнение данных и явные действия разрешения конфликтов.

## Рассмотренные альтернативы

- Блокировать редактирование, пока кампания на сервере: неудобно для подготовки между сессиями.
- Автоматический merge по полям: непрозрачно для пользователя.
