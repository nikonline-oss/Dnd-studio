# 0060. Подписанный индекс плагинов: подписываемые байты и ключ доверия

- Статус: Принято; реализация — `ring` вместо `ed25519-dalek` (см. ниже)
- Дата: 2026-11-08

## Контекст

ADR-0006 выбрал статический подписанный индекс в отдельном репозитории, но не зафиксировал
точные подписываемые байты, вид ключа и поведение при отзыве. Без этого `sign` и `index` в
CLI (R3.2) можно реализовать по-разному на стороне публикации и на стороне клиента, и подпись
перестанет что-либо доказывать. Этот документ фиксирует формат до реализации.

## Решение

### Подпись пакета

Подписывается не архив, а короткий транскрипт, привязанный к личности и версии:

```
"dndstudio-plugin-v1\n" + id + "\n" + version + "\n" + sha256_hex(archive)
```

- `id` и `version` — из `manifest.json` уже распакованного пакета, в каноническом виде как в
  манифесте;
- `sha256_hex` — нижний регистр, 64 символа: тот же хэш, что в `installed_plugins.archive_sha256`;
- доменный префикс отделяет эти подписи от подписи индекса и обновлений приложения.

Подпись — ed25519, 64 байта, хранится как 128 символов нижнего регистра. Пакет без подписи
устанавливается локально как «неподписанный» с предупреждением; из каталога — только с
проверенной подписью.

Почему транскрипт, а не архив целиком: архив уже адресуется по SHA-256, а подпись над
транскриптом дополнительно связывает байты с `id`/`version`. Подменить пакет, сохранив подпись,
нельзя: изменится хэш, а перенести подпись на другой `id`/`version` — тоже.

### Индекс

Файл `index.json` — ровно те байты, которые подписаны (никакой нормализации при проверке):

```json
{
  "format": 1,
  "key_id": "catalog-2026",
  "generated_at": "2026-11-08T12:00:00Z",
  "plugins": [
    {
      "id": "srd5",
      "version": "0.13.0",
      "kind": "system",
      "license": "CC-BY-4.0",
      "app_compat": ">=0.0.1, <0.2.0",
      "sha256": "…64 hex…",
      "archive_url": "https://github.com/…/releases/download/srd5-0.13.0/srd5-0.13.0.dndplugin",
      "signature": "…128 hex…",
      "revoked": false,
      "dependencies": { "core-rules": "^1.0" }
    }
  ]
}
```

- Подпись индекса — отдельный файл `index.sig` (hex), вычисленный по **точным байтам**
  `index.json` с доменным префиксом `"dndstudio-index-v1\n"`.
- Клиент проверяет: подпись индекса → `format` и `key_id` → для выбранного пакета `sha256` и
  подпись пакета → `manifest` внутри архива. Несовпадение `id`/`version` между индексом и
  манифестом — отказ.
- `key_id` позволяет сменить ключ, не ломая старые индексы: приложение хранит список принятых
  `(key_id, public_key)`. Неизвестный `key_id` — отказ, а не «доверяем на слово».

### Отзыв

`"revoked": true` означает: новые установки и обновления этой версии запрещены; уже
установленная копия продолжает работать, но помечается предупреждением. Отзыв не удаляет данные
и не отключает кампанию — это решение мастера.

### Публикация

- Приватный ключ — только в секретах CI репозитория каталога; в артефактах и логах его нет.
- Workflow: валидация пакета (`plugin-tool validate`) → упаковка (`pack`, воспроизводимая) →
  подпись (`sign`) → публикация неизменяемого архива в Releases → пересборка и подпись индекса
  (`index`).
- Опубликованная версия неизменяема: повторная публикация того же `id`/`version` с другим
  хэшем — ошибка, а не обновление. Исправление — новая версия.

## Реализация

- `dnd_plugin::signature`: транскрипты, проверка подписи пакета и индекса, hex.
- `dnd_plugin::catalog`: строгое чтение подписанного индекса (подпись проверяется до разбора),
  выбор новейшей совместимой версии, запрет отозванных, `verify_package` (SHA-256 → подпись →
  разбор пакета → сверка `id`/`version`).
- `plugin-tool keygen | sign | index`: генерация ключа в PKCS#8 (права 0600), подпись одного
  пакета, сборка и подпись индекса. Повторная публикация той же версии с другим хэшем — ошибка.

**Отклонение от §3 CLAUDE.md:** вместо `ed25519-dalek` используется `ring`. Причина: `ring` уже
в дереве зависимостей (TLS через rustls), а `ed25519-dalek` в среде подготовки отсутствовал и
сеть была закрыта. Алгоритм тот же (Ed25519), поэтому формат подписи не меняется; замена
библиотеки позже не затронет ни один подписанный артефакт. Ключ хранится в PKCS#8 (DER), а не как
32-байтовый seed — это требование `ring` и осознанный компромисс: CI получает файл ключа.

Загрузка и кэш реализованы в `dnd-net`, экран каталога — в десктоп-клиенте; подпись
перепроверяется перед активацией. Сетевое чтение ограничено фактически полученными байтами:
индекс — 16 МиБ, подпись — 1 КиБ, архив — 256 МиБ (как `PackageLimits::DEFAULT`).
Проверка `Content-Length` выполняется заранее, но не заменяет лимит потока. Кэш проверяется
по размеру и читается с тем же пределом; повреждённая копия скачивается повторно.
Превышение лимита возвращает стабильный код `download_too_large`.

## Рассмотренные альтернативы

- **Подписывать архив целиком.** Дороже по памяти на больших пакетах и ничего не добавляет:
  хэш уже адресует содержимое.
- **Подпись внутри ZIP (`signature.json`).** Меняет хэш архива после подписи и требует двух
  проходов; внешняя подпись проще и не влияет на `sha256`.
- **Подписывать нормализованный JSON индекса.** Требует канонизации на обеих сторонах; подпись
  точных байтов файла исключает расхождение.
- **Один ключ навсегда.** Ротация без `key_id` означала бы «обновите приложение, чтобы получить
  новые плагины»; список принятых ключей решает это мягче.
