# 0034. Ручные групповые запросы бросков

- Статус: Принято (P1, MVP идеи GM-5)
- Дата: 2026-11-02

## Контекст

Скрытый бросок GM/Co-GM уже доступен через `/gr` и `/gmroll`. Запросы бросков,
уведомления и ответы существуют для ресурсных действий триггеров, но обычную проверку
мастер не мог запросить без создания триггера. Нужен тот же механизм уведомлений
и контроля владельца персонажа, с отдельной итоговой сводкой.

## Решение

Новый Create-intent `RequestRolls { id, label, dice, characters }` разрешён только GM/Co-GM.
Ядро атомарно проверяет название, формулу, существование и активный статус всех целей,
уникальность списка, ссылки на числовые поля каждого листа и лимиты. До 20 персонажей
в одном запросе; действующий общий предел хранимых запросов `MAX_ROLL_REQUESTS` сохраняется.
Проверка формулы при создании не бросает кубы и не расходует игровой RNG.

Создаются обычные `RollRequested`, проецируемые в существующие JSON-строки SQLite.
В `RollRequestDto` источник `trigger` становится опциональным; новый `group` содержит ID
первого запроса группы. У проверок `trigger = None`, у прежних запросов от триггеров
`group = None`. Запросы группы не наносят урон и не меняют ресурсы. Старые строки со
строковым `trigger` читаются как `Some`, отсутствующий `group` — как `None`.
Новых таблиц и SQL-запросов нет.

Ответ — прежний Checked-intent `FulfillRollRequest`. Игрок отвечает только за своего
персонажа, GM/Co-GM — за любого; Spectator не отвечает. Формула читается из запроса,
поля — из текущего листа персонажа. Результат создаёт публичный бросок с ID фактического
отправителя и связью с персонажем. Результаты от триггеров сохраняют прежнюю семантику.
Входящие запросы видны только владельцу и GM/Co-GM (ADR-0031), уведомляет PLR-3.

Когда последняя ожидающая проверка группы выполнена либо отменена, ядро добавляет
одно `ChatMessagePosted` с `SystemMessage::RollsCollected`. Сводка содержит имена,
итоги и отменённые ответы и имеет `ChatVisibility::Gm`. Она не попадает игрокам ни
в WS-событиях, ни в снапшоте, ни в HTTP-истории. Последующая отмена уже завершённого
результата не перепубликует сводку: она остаётся историческим сообщением на момент
завершения группы. Удаление персонажа отменяет его ожидающие запросы и тоже может
завершить группу. Перевод персонажа другому владельцу следует ADR-0031.

## Интерфейс

GM/Co-GM открывает «Запросить броски» из чата: название, формула и выбор активных персонажей.
«Все игроки» выбирает активных PC, принадлежащих пользователям с ролью Player; NPC и другие
персонажи выбираются вручную. При нескольких PC у игрока выбираются все такие персонажи.
Игрок без активного персонажа не получает проверку. Лимиты и причины незаполненной формы
видны до отправки; отказ формулы/полей не закрывает форму. Повторная отправка из той же
формы использует тот же ID группы и не создаёт вторую группу.

## Последствия

Версия протокола повышается до 10: появились новый intent, вариант системного сообщения
и nullable-источник запроса. Клиент и сервер нужно обновлять вместе. Сервер остаётся
авторитетным; локальная игра использует тот же pipeline. Новых зависимостей нет.

Личные броски конкретному игроку и отдельный приватный канал не входят в MVP этого среза;
они остаются расширением GM-5/PLR-7. Скрытые броски по действующей модели доступны обеим
ролям мастера, а не персональному аккаунту одного GM.

## Проверки

Ядро: все роли, контроль владельца, версии и повтор ответа, ошибки формулы/полей,
пустые/повторные/неизвестные цели, архивные персонажи, атомарность, отсутствие ресурсных
изменений, единственная сводка, отмена и удаление персонажа. SQLite: legacy defaults.
LocalServer: переоткрытие и идемпотентный повтор. Реальный WS: два игрока, персональные
запросы, ответ игрока, сводка мастеру и исключение её из истории игрока. UI: выбор,
ошибки без потери данных, все роли и отображение сводки.
