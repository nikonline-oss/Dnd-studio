# 0051. Версия сохранённого процесса правил

- Статус: Принято
- Дата: 2026-11-08

## Контекст

`plugin_runtime` хранится одной строкой JSON в таблице `plugin_runtime` (миграция 0024) и
описывает незавершённое действие: ожидающие спасброски, объявленное действие с реакцией,
поддерживаемые эффекты, предложения реакции на движение. Это состояние принадлежит версии
приложения, а не кампании: новая сборка может изменить структуру полей.

До этого решения версии не было: `dnd-db` читал JSON напрямую через `serde_json::from_str` с
`#[serde(default)]` у полей. Ошибка чтения выглядела как ошибка БД, а несовместимая структура
могла молча превратиться в пустой runtime — то есть в потерянное ожидание посреди боя
(дорожная карта A6.1).

## Решение

### Хранение

Строка в `plugin_runtime.dto` получает оболочку:

```json
{ "version": 1, "runtime": { "saves": [], "movements": [], "...": "..." } }
```

`dnd_db::RUNTIME_VERSION` — версия, которую пишет эта сборка. Менять её обязательно при любом
несовместимом изменении `PluginRuntime`; вместе с повышением добавляется путь чтения прежней
формы. Форма на проводе (`Snapshot`, `Event::PluginRuntimeUpdated`) не меняется: версия — деталь
хранения, а не протокола, и клиент не должен о ней знать.

### Чтение

- **Без поля `version`** — файл, сохранённый до этого решения. Читается как обычный
  `PluginRuntime` (все поля имеют значения по умолчанию), то есть кампания с ожидающим
  действием продолжается. При следующей записи runtime получает версию сам собой.
- **Версия меньше или равна `RUNTIME_VERSION`** — читается как есть. Сейчас это только текущая
  форма; для будущих версий здесь появится миграция.
- **Версия больше `RUNTIME_VERSION`** — `DbError::RuntimeTooNew { version, supported }`:
  кампанию открыла более старая сборка, чем та, что её сохранила. Сообщение просит обновить
  приложение, как и `SchemaTooNew` для миграций схемы.
- **Битый JSON, нечисловая версия, версия без payload** — `DbError::InvalidData` с указанием
  колонки. Пустой runtime вместо ошибки не подставляется.

Ошибка чтения остаётся ошибкой: `CampaignDb::open`/`load_state` возвращают её наверх, локальный
сервер и сессия не открываются с «пустыми» ожиданиями.

### Запись

Пишется всегда текущая версия, независимо от того, в какой форме runtime был прочитан. Поэтому
кампания обновляется при первом же изменении правил, и старая форма не тянется бесконечно.

## Последствия

- Пользователь старой сборки, открывший кампанию из новой, получает понятный отказ, а не
  испорченное состояние.
- Обновление приложения не теряет ожидающие действия: старый JSON валиден и продолжает
  работать.
- `PluginRuntime` остаётся типа из `dnd-protocol`; версия живёт в `dnd-db`, ближе всего к
  хранению, и не протекает в сетевой контракт.
- Тесты: unit-тесты `dnd_db::runtime_store` (round-trip, legacy, будущая версия, битый JSON) и
  интеграционные `crates/dnd-db/tests/runtime_store.rs` (открытие кампании с legacy-строкой,
  отказ для будущей версии, запись с версией).

## Рассмотренные альтернативы

- **Поле `version` внутри `PluginRuntime`.** Проще, но меняет сетевой DTO и TS-bindings ради
  детали хранения; клиенту версия процесса не нужна.
- **Новая колонка `version` в таблице.** Потребовала бы миграции схемы ради одного числа;
  оболочка в JSON обходится без неё и переносится вместе с кампанией при экспорте.
- **Отдельная таблица истории runtime.** История не нужна: важен только текущий незавершённый
  процесс, а журнал событий уже хранит, как он возник.
