# 0014. Write-through: события пишутся до рассылки

- Статус: Принято. Заменяет [0011](0011-autosave-and-backups.md) в части автосохранения.
- Дата: 2026-10-21

## Контекст

ADR-0011 буквально следовал прежней формулировке §10 («debounce грязного состояния 2 с»): intent
применялся в памяти, а batch событий записывался в SQLite через 2–10 с. При краше терялось до 10 с
правок, память опережала диск, а клиенты получали события, которых ещё нет на диске. Для сервера
сессий эта модель ещё хуже: клиент мог применить событие, которое после краша сервера «исчезнет».

## Решение

- **Write-through.** `apply` → запись batch одной транзакцией (`event_log` + проекция) → только после
  коммита `evolve` в памяти и рассылка события (`GameEventsEmitted`, позже — WS-клиентам).
- Ошибка записи: состояние в памяти, файл и счётчик `seq` не меняются, intent возвращает `IpcError`
  (`storage_error`). Следующий intent продолжает с того же `seq`.
- Рассылка идёт под тем же замком, что и запись, поэтому события уходят строго в порядке `seq`.
- «Автосохранение» = WAL checkpoint каждые 5 минут и при закрытии кампании/выходе. Для сохранности
  данных он не нужен: всё уже в WAL.
- Debounce 2 с остаётся только для UI-черновиков (редактор журнала, поля форм) — CLAUDE.md §10 уточнён.
- Индикатор «несохранённые изменения» убран: несохранённого состояния больше нет.
- `Ctrl+S` (`campaign_checkpoint`) — принудительный WAL checkpoint с тостом «Сохранено»: после него
  один `campaign.sqlite` полностью актуален (например, перед ручным копированием файла).
- Бэкапы и восстановление — без изменений (ADR-0011, ADR-0008): `VACUUM INTO`, ≤ 5 штук, бэкап при
  открытии, если последнему больше 24 ч.

## Последствия

- При краше теряется не больше одного intent, который ещё не закоммичен (и клиенту он не подтверждён).
- Транзакция на каждый batch: с WAL и `synchronous=NORMAL` это порядка миллисекунды; перетаскивание
  токенов на 10–15 Гц (ADR-003) укладывается с запасом. Если профилирование покажет иное, группировать
  будем на уровне throttling ввода, а не откладыванием записи.
- Та же модель без изменений переносится на сервер сессий (этап 2b).
