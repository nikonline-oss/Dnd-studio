# Self-hosting сервера сессий

Сервер сессий — один контейнер: axum + игровое ядро + SQLite. Мастер загружает кампанию,
сервер исполняет игру авторитетно, игроки подключаются по WebSocket. Прямого канала
мастер↔игрок нет (CLAUDE.md §1, ADR-0022).

## Что нужно

- Docker Engine 24+ с плагином Compose v2 (`docker compose version`);
- домен, если нужен HTTPS (для локальной сети достаточно IP и порта);
- 1 vCPU и 512 MiB RAM на небольшой стол; диск — по размеру кампаний и ассетов.

## Быстрый старт

```bash
git clone <репозиторий> dndstudio && cd dndstudio
cp .env.example .env
# Обязательно: длинный случайный секрет. Он даёт право загружать кампании.
openssl rand -base64 32   # вставьте в DND_HOST_TOKEN
$EDITOR .env
docker compose up -d --build
curl -fsS http://127.0.0.1:8080/api/health
```

Успешный ответ healthcheck означает, что сервер поднялся. Дальше:

1. В десктопе откройте кампанию → «Хостинг» → укажите адрес сервера и host token.
2. Загрузите кампанию: сервер вернёт `gm_key`, код доступа и ссылку-приглашение.
3. Игроки подключаются по ссылке и коду доступа (или вводят адрес и код вручную).
4. Остановка сессии мастером возвращает финальную копию кампании на его машину.

## Настройка

Все переменные читаются из `.env` (см. `.env.example`). Обязательна только `DND_HOST_TOKEN`
(≥ 16 символов) или `DND_HOST_TOKEN_FILE` с секретом в файле.

| Переменная                   | По умолчанию               | Смысл                                                       |
| ---------------------------- | -------------------------- | ----------------------------------------------------------- |
| `DND_HOST_TOKEN`             | —                          | право загружать кампании; не публикуйте его                 |
| `DND_HOST_TOKEN_FILE`        | —                          | альтернатива: путь к файлу с секретом                       |
| `DND_DATA_DIR`               | `/data`                    | данные сервера (в контейнере)                               |
| `DND_BIND`                   | `0.0.0.0:8080`             | адрес внутри контейнера                                     |
| `DND_PUBLIC_URL`             | из запроса (`Host`)        | база ссылок-приглашений, например `https://dnd.example.org` |
| `DND_MAX_SESSIONS`           | 100                        | одновременных сессий                                        |
| `DND_MAX_PARTICIPANTS`       | 20                         | участников в сессии                                         |
| `DND_SESSION_TTL_SECS`       | 3600                       | простой до истечения сессии                                 |
| `DND_CONNECTIONS_PER_MINUTE` | 10                         | лимит подключений на IP                                     |
| `DND_MESSAGES_PER_MINUTE`    | 100                        | лимит сообщений на соединение                               |
| `DND_MAX_UPLOAD_MB`          | 1024                       | размер загружаемого архива                                  |
| `DND_PORT`                   | 8080                       | порт на хосте (compose)                                     |
| `DND_BIND_ADDR`              | `0.0.0.0`                  | интерфейс хоста для опубликованного порта (compose)         |
| `DND_DOMAIN`                 | —                          | домен для профиля TLS (compose)                             |
| `DND_SERVER_IMAGE`           | `dnd-session-server:local` | готовый образ вместо локальной сборки (compose)             |
| `RUST_LOG`                   | `info`                     | уровень логов                                               |

## HTTPS

### Вариант 1: профиль Caddy (автоматические сертификаты)

```bash
# .env
DND_DOMAIN=dnd.example.org
DND_BIND_ADDR=127.0.0.1      # порт приложения доступен только локально
DND_PUBLIC_URL=https://dnd.example.org

docker compose --profile tls up -d
```

Caddy сам получит и продлит сертификат (нужны открытые 80 и 443 и DNS-запись на этот хост).
WebSocket и загрузки ассетов проксируются без дополнительной настройки. `DND_BIND_ADDR=127.0.0.1`
важен: приложение не терминирует TLS и не должно быть доступно в обход Caddy.

### Вариант 2: свой reverse proxy

Сервер работает и за чужим прокси: достаточно проксировать HTTP и WebSocket на `127.0.0.1:8080`.
Задайте `DND_PUBLIC_URL`, чтобы ссылки-приглашения были правильными.

**Ограничение rate limit.** Лимит подключений считается по IP соединения. За прокси это адрес
прокси, поэтому либо поднимите `DND_CONNECTIONS_PER_MINUTE`, либо ограничивайте подключения на
самом прокси.

## Данные и бэкап

В томе `dnd-data` (внутри — `/data`):

```
server.sqlite                 сессии, участники, аудит; секреты только как хэши
sessions/{id}/campaign.sqlite кампания сессии (та же схема, что у десктопа)
sessions/{id}/assets/         ассеты сессии
tmp/                          загрузки и экспорты в процессе
```

Согласованная копия:

```bash
# Остановить сервер, чтобы ни одна сессия не писала в файлы.
docker compose stop session-server
docker run --rm -v dndstudio_dnd-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/dnd-data-$(date +%F).tgz -C /data .
docker compose start session-server
```

Почему остановка: `campaign.sqlite` работает в WAL, и копирование «на живую» без
`sqlite3 .backup` может дать несогласованный файл. Если остановка невозможна, попросите мастера
экспортировать кампанию (`GET /api/sessions/{id}/export`) — сервер отдаёт согласованный архив.

Имя тома — `<папка репозитория>_dnd-data`; проверьте `docker volume ls`.

Восстановление в новый том:

```bash
docker compose down
docker volume create dndstudio_dnd-data
docker run --rm -v dndstudio_dnd-data:/data -v "$PWD":/backup alpine \
  tar xzf /backup/dnd-data-2026-01-01.tgz -C /data
docker compose up -d
curl -fsS http://127.0.0.1:8080/api/health
```

Уже загруженные сессии продолжают работать: сессия — это файл, а не процесс в памяти. Сессия,
истёкшая или остановленная до копии, останется в том же статусе.

## Обновление и откат

```bash
# Обновление из исходников
git pull && docker compose up -d --build

# Готовый образ из GHCR
DND_SERVER_IMAGE=ghcr.io/OWNER/REPO/session-server:0.2.0 \
  docker compose up -d --pull always --no-build
```

Перед обновлением сделайте бэкап тома. Миграции БД идут только вперёд: сервер старой версии не
откроет файл, созданный новой, и скажет об этом при старте. Поэтому откат образа делайте вместе с
откатом тома.

## Эксплуатация

- **Логи:** `docker compose logs -f session-server`; ограничьте их размер через `log-opts` Docker.
- **Health:** `curl -fsS /api/health`; тот же вызов делает HEALTHCHECK образа.
- **Аудит:** таблица `audit_log` в `server.sqlite` хранит действия мастера.
- **Завершение:** `docker compose stop` даёт 20 секунд на штатное закрытие.
- **TTL:** неактивная сессия истекает через `DND_SESSION_TTL_SECS`; файлы остаются на диске,
  чтобы мастер мог забрать кампанию.

## Если что-то не работает

| Симптом                             | Что проверить                                                |
| ----------------------------------- | ------------------------------------------------------------ |
| `401` при загрузке кампании         | host token в десктопе совпадает с `DND_HOST_TOKEN`           |
| `protocol_mismatch` при подключении | клиент и сервер разных версий: обновите оба                  |
| Игрок не подключается по ссылке     | `DND_PUBLIC_URL` и DNS; порт 443 доступен                    |
| Обрывы раз в минуту                 | прокси закрывает WebSocket: проброс upgrade и таймаут ≥ 60 с |
| `rate_limited` при входе            | лимит подключений на IP; за прокси считайте по IP прокси     |
| Сервер не стартует после обновления | файл создан новой версией: откатите образ и том вместе       |

## Границы

- Сервер не заменяет резервное копирование: том — единственная копия данных.
- TLS, если он нужен, терминируется Caddy или вашим прокси; сам сервер его не делает.
- Почта, аккаунты и маркетплейс не входят в self-hosting MVP.

## Состояние проверки

Проверено 2026-11-09 на Ubuntu 24.04 (Docker 29.1.3):

- сборка образа `docker build -f apps/session-server/Dockerfile .` — успешно;
- запуск контейнера с `DND_HOST_TOKEN` и `DND_PUBLIC_URL` — `GET /api/health` отвечает
  `{"status":"ok","protocol":20}`, порт доступен снаружи;
- загрузка кампании `POST /api/sessions` и вход игрока по коду доступа и мастера по `gm_key`;
- клиент на коде `dnd-net` получает снапшот, отправляет чат и получает рассылку;
- `docker restart` — сессия остаётся `active`, клиент снова подключается;
- `GET /api/sessions/{id}/export` отдаёт согласованный архив (`manifest.json` +
  `campaign.sqlite`);
- игроку приходит только публичное подмножество листа (ADR-0049), проверено на живом сервере.

Не проверено: профиль Caddy/TLS с настоящим доменом и сертификатом, публикация образа в GHCR,
восстановление из копии тома в новый том, Windows-клиент на реальной машине. Эти шаги требуют
внешних ресурсов (домен, registry, Windows-хост) и остаются за R2.3/R2.4 и R4.2.
