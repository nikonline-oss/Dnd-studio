# Протокол

Источник истины — крейт `crates/dnd-protocol`; форма JSON закреплена insta-снапшотами в
`crates/dnd-protocol/tests/snapshots/`, TS-типы — там же (`snapshots__typescript_bindings.snap`).
Решения о кодировании — [ADR-0007](adr/0007-protocol-encoding.md).

## Конверт

```json
{ "v": 1, "id": "<uuid>", "ts": 1760000000000, "seq": null,
  "session_id": "<uuid>|null", "sender": "<uuid>|null",
  "type": "intent", "payload": { ... } }
```

`v` ≠ версии получателя → отказ `protocol_mismatch` («обновите клиент/сервер»).

## Сообщения

| Направление     | `type`              | `payload`                                          |
| --------------- | ------------------- | -------------------------------------------------- |
| клиент → сервер | `intent`            | `{ intent_id, expected_version, intent }`          |
| клиент → сервер | `ping`              | —                                                  |
| клиент → сервер | `resync`            | `{ last_seq }`                                     |
| клиент → сервер | `get_journal_entry` | `{ id }` — текст записи (в снапшоте только индекс) |
| сервер → клиент | `events`            | `{ seq, caused_by, events[] }`                     |
| сервер → клиент | `snapshot`          | полное видимое получателю состояние                |
| сервер → клиент | `accepted`          | `{ intent_id, seq }` — только отправителю          |
| сервер → клиент | `rejected`          | `{ intent_id, reason: { code, ... } }`             |
| сервер → клиент | `journal_entry`     | `{ id, entry }` (`null` — нет или не видна)        |
| сервер → клиент | `pong`              | —                                                  |

Версия протокола — 6 (таблицы и библиотеки ассетов — ADR-0026). Получатель видит не всё (ADR-0022): скрытое от него событие
приходит как `{ "kind": "redacted" }` с тем же номером, а когда видимость меняется целиком
(карту открыли игрокам, токен ушёл на слой мастера) — новый `snapshot`. Событие
`user_joined` создаёт сервер, когда участник входит в сессию; intent'а у него нет.

## Загрузка ассетов сессии (ADR-0004)

`POST /api/sessions/{id}/assets` принимает бинарное тело с `Authorization: Bearer <GM-token>`,
`X-Asset-Sha256: <64 lowercase hex>` и `X-Asset-Kind: webp | audio | plugin`. Файл ограничен
меньшим из лимита загрузки сервера и 100 МиБ; дополнительно действуют лимиты формата аудио/плагинов.
Сервер проверяет роль до чтения тела, SHA-256, формат и безопасно сохраняет файл под вычисляемым именем.
Повтор той же загрузки идемпотентен; успех — `204 No Content`.

Загрузка не регистрирует игровую сущность и не раскрывает файл игрокам. После файлов клиент отправляет
`register_asset` или `install_plugin` обычным пайплайном намерений. Офлайн-очередь сохраняется при ошибке
загрузки, чтобы повторить её с прежним `intent_id`.

## Идемпотентность и повторы (ADR-0015)

- `intent_id` — ключ идемпотентности. Повтор **того же** intent (тот же `intent_id` и те же данные)
  возвращает исходный результат и ничего не применяет. Кэш хранит последние 10 000 intents или 24 ч;
  принятые операции вне кэша находятся по долговечной записи `event_log`, включая после перезапуска.
- Сервер хранит SHA-256 данных intent (`expected_version` + `intent`). Тот же `intent_id` с другими
  данными → `rejected { code: intent_id_reused }`.
- **Любой повтор с изменёнными данными — новый `intent_id`.** Например, после `stale_version` клиент
  перечитывает сущность и отправляет правку с новой `expected_version` под новым id.
- Повторно отправлять неподтверждённый intent после реконнекта нужно с прежним `intent_id` и
  прежними данными.
- `intent_id` и id создаваемых сущностей — UUIDv7. Сервер проверяет только версию и формат UUID;
  временная метка внутри id ничего не значит для правил и прав.
