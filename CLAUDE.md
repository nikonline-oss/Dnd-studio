# DndStudio — контекст проекта для Claude Code

Этот файл — источник истины по продукту и архитектуре. Не добавляй функционал, противоречащий скоупу.
Всё, что выходит за рамки MVP (P0), явно помечай. При неоднозначности — задай вопрос, а не угадывай.
Архитектурные решения фиксируй как ADR в `docs/adr/NNNN-название.md`.

## 1. Что это

Open-source экосистема для настольных ролевых игр, **не привязанная к конкретной системе правил**:
приложение подстраивается под любую НРИ через плагины.

1. **Десктоп-клиент** (Windows/macOS/Linux, Tauri) — рабочее место мастера и игрока: подготовка кампаний,
   локальная игра, подключение к удалённым сессиям.
2. **Сервер сессий** — self-hosted сервис (Docker Compose). Мастер загружает кампанию, сервер исполняет игру
   авторитетно, игроки подключаются к серверу. Прямого канала мастер↔игрок нет.
3. **Каталог плагинов** — в MVP статический подписанный индекс в GitHub-репозитории; полноценный
   сервис-маркетплейс — пост-MVP.

Лицензия: MIT OR Apache-2.0 (если в репозитории не указано иное — спроси).

## 2. Ключевые архитектурные решения (не пересматривать без ADR)

### ADR-001. Единое игровое ядро `dnd-game-core`
Вся игровая логика — чистая детерминированная функция без I/O:
`apply(state, intent, actor, rng) -> Result<Vec<Event>, RuleError>`.
- Сервер сессий = game-core + WS + SQLite сессии.
- Локальная игра = game-core внутри Tauri (in-process «сервер»), **тот же пайплайн намерений**.
- Фронтенд никогда не мутирует данные напрямую: только отправляет intents и применяет events/снапшоты.
  UI-код одинаков для локальной и удалённой игры.
- RNG передаётся в ядро снаружи (в тестах — детерминированный seed).

### ADR-002. Хранилище: SQLite везде
- Кампания на клиенте = один SQLite (WAL) + папка ассетов.
- Сессия на сервере = **такой же SQLite-файл** + ассеты: `/data/sessions/{id}/campaign.sqlite`.
  Одна схема, одни миграции (крейт `dnd-db`), экспорт = отдача файла.
- Индекс сервера (сессии, участники, аудит) — отдельный `/data/server.sqlite`.
- PostgreSQL и S3 в MVP **не используются**. Хранилище файлов — через крейт `object_store`
  (локальная ФС по умолчанию, S3 — опционально пост-MVP).

### ADR-003. Конкурентность: оптимистичные версии, а не приоритет ролей
- У каждой изменяемой сущности поле `version: i64`.
- Мутирующий intent несёт `expected_version`. Несовпадение → `Rejected { reason: StaleVersion, current }`.
- Права (кто *может* менять) проверяет ядро по роли. Приоритет GM применяется только явно:
  GM может отклонить/перебить ожидающий запрос игрока.
- Исключение: позиции токенов — last-write-wins с серверной реконсиляцией, throttling 10–15 Гц.

### ADR-004. Редактирование кампании GM, пока она на сервере
- GM подключён к сессии → его правки идут intents через сервер; локальная БД — реплика, применяющая events.
- GM работает офлайн с выгруженной кампанией → правки пишутся в локальный журнал операций
  (`pending_ops`: intent + base version). При подключении журнал отправляется на сервер по порядку.
  Конфликт (StaleVersion) → серверная версия остаётся, конфликтующая правка попадает в панель
  «Конфликты» с diff и кнопками «применить мою поверх» / «отбросить».
- Ассеты адресуются по SHA-256 — конфликтов не бывает, докачиваются по хэшу.
- Остановка сессии → клиент забирает финальный SQLite, делает бэкап локального и заменяет его.
- Кампания в статусе «на сервере» помечается в UI (строка статуса + бейдж в навигаторе).

### ADR-005. Универсальность систем правил
- **Системный плагин** (`kind: "system"`): ровно один на кампанию. Определяет схемы листов, ресурсы
  (обобщение HP), состояния/кондиции, формулу инициативы, пороги качественного здоровья, макросы бросков.
- Остальные плагины (`kind: "content" | "theme" | "ui"`) расширяют систему или работают поверх любой.
- Ядро не знает слов «сила», «класс брони» и т.п. Есть только: сущности, поля, ресурсы, броски, формулы.
- **Expression language (минимальный) — переносится в P0**, иначе универсальность недостижима:
  арифметика, сравнения, `if/then/else`, `min/max/floor/ceil/round/abs`, ссылки на поля (`@str`, `@hp.max`),
  без циклов, функций пользователя и доступа к чему-либо кроме переданного контекста. Лимит на глубину и
  длину выражения. Полноценный DSL (Фаза 3) — пост-MVP.
- Движок костей (`dnd-dice`): P0 — `NdX`, модификаторы и ссылки на поля (`1d20 + @str_mod`), `d%`,
  keep/drop (`4d6kh3`), adv/dis. P1 — exploding (`!`), пулы с подсчётом успехов (`10d6>=5`), Fate (`dF`).

### ADR-006. Каталог плагинов в MVP = подписанный статический индекс
- Отдельный репозиторий `dndstudio-plugins`: авторы присылают PR с `.dndplugin`.
- GitHub Actions: валидация манифеста, проверки безопасности (§9), подпись ed25519 ключом проекта
  (секрет CI), публикация архива в Releases, обновление `index.json` (тоже подписан).
- Клиент: каталог, поиск по индексу, карточка, установка/обновление в один клик, проверка подписи и SHA-256.
- Опубликованная версия неизменяема. Отзыв версии — флаг `revoked` в индексе.
- Сервис маркетплейса (аккаунты, рейтинги, отзывы, ручная модерация) — **пост-MVP**.

## 5. Роли и права

GM / Co-GM / Player / Spectator. Проверка — всегда в game-core; клиент лишь скрывает UI.
- GM: всё, включая роли, остановку и экспорт сессии.
- Co-GM: как GM, кроме удаления кампании/сессии и изменения ролей GM.
- Player: свои персонажи, видимые данные, чат, броски, движение своих токенов; чужие токены — запросом к GM.
- Spectator: только просмотр (включается настройкой).
- Игрок видит качественное здоровье (Healthy/Wounded/Critical/Dead), пороги — из системного плагина
  (по умолчанию 75/25/0 %).
- Персонаж игрока: draft → pending_approval → active → archived; одобряет GM.
- Пресет раскладки для роли Player: карта + чат + лист персонажа, остальные панели скрыты; слева — полоса
  иконок (журнал, персонажи), боковая панель по умолчанию свёрнута.

## 6. Модель данных (клиент и сессия — одна схема)

visible_to_players), characters (kind, sheet_template, sheet_data JSON, owner, status), tokens (map, character?,
asset?, x, y, rotation, scale, layer, visible), journal_folders (parent, name, order), journal_entries (markdown, folder_id, order, visibility,
players_can_edit), journal_links (source, target_type, target_id, link_type, directed, weight, label, meta,
visible_to_players), compendia + compendium_entries, installed_plugins (id, version, active, config,
installed_at, compat_warning), chat_messages (append-only, `sender_name` на момент записи), dice_rolls
(`user_name` на момент записи), event_log (seq, event JSON),
combats (map — один бой на карту, round, turn) + combatants (combat, token?, character?, name, initiative?,
sort_order) — ADR-0020, boards + board_nodes + board_edges, zones (на картах, только GM), triggers
(только GM; данные «Когда → Если → Тогда», исполняет ядро), characters.conditions — ADR-0024,
pending_ops (только клиент, ADR-004).
У всех изменяемых сущностей — `version`. Архив кампании: ZIP = `campaign.sqlite` + `assets/` + `manifest.json`.

Сервер, `server.sqlite`: sessions (id, state: creating/active/stopped/expired, params, gm_key_hash,
access_code_hash, created_at, last_activity, storage paths), participants (session, role, name, connected_at,
status), audit_log (действия GM). Ключи и коды — только хэши (argon2).

## 7. Протокол (WS, JSON в MVP)

Конверт: `{ v, id, type, ts, seq, session_id, sender, payload }`. Одна версия протокола; несовпадение → отказ
с понятной ошибкой «обновите клиент/сервер».
- Клиент → сервер: `Intent { expected_version?, ... }`, `Ping`, `Resync { last_seq }`, `GetJournalEntry { id }`.
- Сервер → клиент: `Events { seq, events[] }`, `Snapshot`, `Accepted { intent_id, seq }`, `Rejected { intent_id, reason }`,
  `JournalEntry { id, entry? }`, `Pong`. Скрытое от получателя событие приходит как `Redacted` (ADR-0022).
- Сервер ведёт `event_log`; при переподключении клиент шлёт `last_seq` и получает дельту или полный снапшот.
- Фильтрация видимости — на сервере, для каждого получателя (скрытые токены, GM-записи журнала, точное HP).
- Реконнект: экспоненциальный backoff 1→30 с. Офлайн-очередь до 100 сообщений: только чат (< 5 мин) и
  движение токенов; прочие мутации после реконнекта не переигрываются вслепую (кроме pending_ops GM по ADR-004).
- Лимиты: 100 активных сессий, 20 участников, сообщение ≤ 64 КБ, heartbeat 15 с, таймаут 45 с,
  TTL неактивной сессии 1 ч, rate limit 10 подключений/мин на IP и 100 сообщений/мин на подключение.
  Всё настраивается конфигом.

HTTP API сервера:
`POST /api/sessions` (требует host token, multipart-архив) → `{ session_id, gm_key, access_code, invite_url }`;
`GET /api/sessions/{id}`; `POST /api/sessions/{id}/join` (`gm_key` или код доступа + имя → токен участника,
ADR-0022; токен — `Authorization: Bearer` для WS и ассетов); `POST /api/sessions/{id}/stop` (GM); `GET /api/sessions/{id}/export` (GM);
`POST /api/sessions/{id}/assets` (GM); `GET /api/sessions/{id}/assets/{sha256}` (участники);
`GET /api/health`; `WS /ws/sessions/{id}`.
**Host token** задаёт владелец сервера в конфиге: только с ним можно создавать сессии (защита self-hosted
сервера от посторонних загрузок). GM-ключ хранится на клиенте в OS keychain.

## 8. Плагины

`.dndplugin` = ZIP: `manifest.json` (id, name, version semver, kind, authors, license, app_compat semver range,
dependencies), ассеты, схемы листов (JSON Schema + layout), компендии, шаблоны кампаний, темы, типы связей.
Формат — `docs/plugin-format.md`; плагины хранятся внутри кампании, правила системного плагина — часть
состояния игры, ядро перепроверяет их само (ADR-0023).
- Шаблоны триггеров (`triggers/`) — данные, не код; состояния (`conditions`) и инвентарь (`inventory`)
  объявляет системный плагин (ADR-0024).
- Лист персонажа: JSON Schema данных + декларативный layout из предустановленных React-компонентов + слоты.
  Вычисляемые поля и кнопки бросков — через `dnd-expr`/`dnd-dice`.
- Установка: drag-and-drop, из файла, из каталога. Разрешение зависимостей; несовместимые деактивируются
  с уведомлением. Safe Mode — запуск без плагинов.

## 9. Безопасность (обязательно)

- Плагины не исполняют код. Темы — **только значения CSS-переменных из whitelist**, никакого сырого CSS
  и внешних `url()`. SVG в плагинах и ассетах растеризуется или санитизируется. Markdown — только через
  rehype-sanitize. Строгий CSP в Tauri, без remote-ресурсов.
- Доступ к ФС — только в директории данных приложения и явно выбранных пользователем файлах.
- Все IPC-команды типизированы и валидируются в Rust. Ошибки на границе IPC — единый `IpcError
  { kind: Recoverable|User|Internal|Fatal, code, message }`.
- Подпись: обновления — minisign; плагины — ed25519 (проверка подписи и SHA-256 перед активацией).
  Отображать уровень доверия: подписан каталогом / локальный неподписанный (с предупреждением).
- Сервер: проверка прав на каждом сообщении, изоляция сессий (отдельные файлы и директории), лимиты
  размеров, хэши секретов, аудит действий GM, безопасная распаковка ZIP (zip-slip, zip-bomb, лимиты).

## 10. Надёжность клиента

WAL; события пишутся write-through: каждый batch events = одна транзакция (`event_log` + проекция),
и только после коммита событие уходит в UI/клиентам (ADR-0014). Debounce 2 с — только для UI-черновиков
(редактор журнала, поля форм), не для событий. WAL checkpoint каждые 5 мин; graceful shutdown. `PRAGMA quick_check` при открытии,
восстановление из последнего бэкапа. Бэкап перед миграцией, максимум 5 бэкапов рядом с кампанией.
Error Boundary на каждую фичу. Safe Mode: предложение после 3 крашей подряд и пункт меню.
Логи: панель (по умолчанию warn+error), ротация 5 × 10 МБ. Автообновление: проверка раз в 24 ч, stable-канал.

## 11. UI

IDE-раскладка: меню + хлебные крошки; полоса иконок (Activity Bar, как в VS Code) и левая панель с одним
разделом (навигатор, плагины, компендии); центр — вкладки и split-view;
правая (инспектор, оглавление журнала); нижняя (чат, логи, позже — терминал DSL); строка статуса (кампания,
статус сервера, активные плагины, версия). Тёмная/светлая тема по системе. Экраны: подключение к сессии,
хостинг (сервер, host token, загрузка, статус, приглашения, QR), каталог плагинов.

## 12. Скоуп

**P0 (v0.1.0)**: кампании (создание/открытие/экспорт/импорт); карта (загрузка, сетка, зум/пан, ручной туман);
токены; движок костей (P0-часть ADR-005); чат с системными сообщениями; инициатива (формула из системного
плагина); журнал (Markdown, папки, видимость, редактирование игроками); персонажи со статусами и одобрением;
просмотр компендиев; ядро плагинов + системные плагины + декларативные листы + **минимальный expression
language**; установка из файла; каталог плагинов на статическом индексе; сервер сессий (создание, загрузка,
подключение, синхронизация, роли, реконнект/ресинк, остановка, экспорт, ADR-004); Docker Compose + документация
self-hosting; автообновление; автосохранение, бэкапы, Safe Mode; i18n RU/EN.
**Расширение P0 по запросу владельца (ADR-0024)**: поля (несколько на кампанию: заметки, ссылки,
картинки, связи, видимость по GM/игрокам), зоны на картах, триггеры-данные (бросок в зоне, вход в зону,
кнопка мастера, получение предмета → раскрытие, чат, броски, урон, состояния, предметы), шаблоны
триггеров в плагинах.

**P1**: HP/ресурсы на токенах с качественными состояниями; расширенные кости; создание компендиев в UI;
импорт JSON/YAML; темы-плагины; delta-докачка ассетов; фильтры каталога; полный набор горячих клавиш;

**P2 / пост-MVP**: сервис маркетплейса (аккаунты, рейтинги, отзывы, ручная модерация); полноценный DSL (Фаза 3)

**Вне скоупа**: LAN и P2P между клиентами, визуальный конструктор плагинов, мобильная версия, Wasm-плагины,
монетизация.

## 13. Этапы

1. **Фундамент** — workspace, `dnd-protocol`, каркас `dnd-game-core` (intent→event на 2–3 сущностях),
   схема и миграции `dnd-db`, локальный «сервер» в Tauri, tauri-specta IPC, IDE-раскладка, темы, i18n,
   логи, автосохранение/бэкапы, CI на 3 платформы, автообновление.
2. **Стол + тонкий удалённый срез** — карта/Pixi, токены, кости, чат, инициатива, журнал, персонажи;
   параллельно каркас сервера сессий: создание, загрузка, WS, синхронизация токенов/костей/чата.
3. **Плагины и системы правил** — формат, загрузчик, зависимости, `dnd-expr`, листы, компендии,
   два системных плагина, безопасные темы, связи журнала.
4. **Сервер полностью** — все сущности через ядро, фильтрация видимости, ресинк, экспорт, ADR-004,
   Docker Compose, self-hosting docs.
5. **Каталог и полировка** — plugin-tool, индекс, подписи, установка/обновление из каталога; горячие клавиши,
   сквозные ошибки, производительность, E2E ключевых сценариев, бета.

## 14. Правила работы

- Работай вертикальными срезами: каждая фича доводится до «работает end-to-end + тесты», а не слоями.
- Любая мутация — новый вариант `Intent` и `Event` в `dnd-protocol` + обработчик в game-core + тесты ядра
  (включая проверку прав для каждой роли) + проекция в `dnd-db`.
- Не добавляй зависимостей сверх §3 без короткого обоснования в PR/ADR.
- `unwrap()`/`expect()` запрещены вне тестов и `main`-инициализации. Никаких `any` в TS.
- Перед завершением задачи: `cargo fmt --check`, `cargo clippy --workspace -- -D warnings`, `cargo test`,
  `pnpm -r lint typecheck test` — всё зелёное.
- Если требование противоречит этому файлу или неоднозначно — остановись и спроси.
